# SH-25 — Validation humaine et tentative SMTP unitaire

## Parcours

Après enregistrement d'un brouillon complet, le recruteur habilité relit destinataire, objet et texte, coche la confirmation puis approuve cette version exacte. Une seconde action demande son envoi. L'approbation dure 30 minutes et conserve validateur, date, version de brouillon, adresse d'expédition/réponse, destinataire et empreinte SHA-256 du contenu exact et de ses références. Les modifications locales masquent l'action d'envoi ; sauvegarder une nouvelle version invalide les approbations antérieures. Il faut relire et approuver la nouvelle version.

L'API de préparation reste sans envoi. `sendBlocked` sur un brouillon signifie qu'un brouillon seul n'autorise jamais la transmission. `POST /candidates/{candidate}/contact-deliveries` exige la confirmation et le texte exacts du dernier brouillon enregistré. `POST /.../{id}/send` effectue au plus une tentative par approbation. `GET /.../{id}` consulte le résultat privé ; ce ticket ne livre pas encore l'historique global SH-26.

## Contrôles à l'envoi

Compte actif, appartenance au vivier, accès aux contacts, rétention, publication courante, destinataire courant, politique active, dossier de traitement complet et absence d'opposition sont recontrôlés. Le lien d'opposition doit être émis pour ce candidat, non expiré et présent dans le texte approuvé : un simple lien HTTPS saisi librement ne suffit pas. Un changement de destinataire, publication, expéditeur ou contenu rend l'approbation inutilisable. ADMIN seul ne donne aucun droit de contact. CSRF est exigé sur approbation et envoi.

Le verrou candidat partagé avec SH-31 est conservé pendant la tentative SMTP bornée. Une opposition déjà enregistrée avant la prise en charge empêche le contact. Une opposition concurrente est sérialisée avec l'envoi ; un message déjà accepté par le relais ne peut pas être rappelé. Seuls les brouillons du validateur sont utilisables. Message unitaire en texte brut, sans pièce jointe, HTML actif ni pixel de suivi ; adresses uniques validées, en-têtes contrôlés.

## Résultats et pannes

Le marqueur `SENDING` est **commité avant** l'appel au relais. Les doubles clics et requêtes répétées retournent l'état existant sans rappeler SMTP. Résultats : `ACCEPTED` signifie accepté par le relais, pas délivré/lu ; `FAILED` désigne une erreur de préparation avant transmission ; toute exception de transport donne `UNCERTAIN`. Aucun renvoi automatique, aucune file de reprise SMTP.

Un crash ou une erreur de persistance après la prise en charge laisse le marqueur durable. La consultation après deux minutes le classe `UNCERTAIN`, sans nouvelle tentative. Les timeouts connexion/lecture/écriture sont de 5 secondes chacun. Après résultat incertain, vérifier la messagerie avant de créer volontairement une nouvelle version et une nouvelle approbation. Cette action manuelle n'est pas une garantie d'absence de doublon chez le destinataire.

Le suivi conserve l'identifiant RFC `Message-ID` stable et le code de résultat ; SMTP standard ne garantit pas un identifiant fournisseur distinct. Aucun accusé de livraison/lecture n'est inventé. Les événements SH-30 n'incluent ni corps, ni destinataire, ni secrets. Les données de livraison privées sont supprimées en cascade avec la candidature ; la purge complète et la politique d'historique restent SH-32/SH-26. Le ticket ne prétend pas offrir un envoi exactement une fois de bout en bout.

## Configuration et recette

Hors compose local, SMTP est désactivé par défaut. Variables : `SMTP_ENABLED`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_SENDER`, `SMTP_STARTTLS`. STARTTLS est activé et exigé par défaut ; renseigner les secrets dans l'environnement, jamais dans le dépôt ou une API de lecture de configuration. Changer la configuration d'expéditeur nécessite une nouvelle relecture.

Le compose local utilise Mailpit v1.33.1 épinglé par digest, sans relais sortant : SMTP interne `mailpit:1025`, interfaces hôte uniquement `127.0.0.1:1025` et `127.0.0.1:8025`. STARTTLS est désactivé uniquement dans cette recette locale. L'API démarre Mailpit avec ses dépendances. Pour l'API Java locale, démarrer Mailpit avec compose et définir `SMTP_ENABLED=true SMTP_HOST=localhost SMTP_PORT=1025 SMTP_STARTTLS=false SMTP_SENDER=no-reply@example.com`.

Tests : refus d'approbation sans relecture exacte, modification après approbation, refus après opposition/changement de destinataire/expiration du lien/révocation, concurrence de deux demandes, timeout ambigu sans renvoi, reprise d'un marqueur interrompu, CSRF et accès privé. La CI ajoute une véritable transmission vers Mailpit puis vérifie dans sa boîte de capture le destinataire, l'objet, le texte et l'unicité du Message-ID. Les tests navigateur vérifient l'accord explicite et la disparition de la validation après édition à 1280/320 px. Les tests locaux sans Mailpit ignorent explicitement la recette réseau.

Commandes : `mvn -f services/api/pom.xml test`, `npm --prefix apps/web run build`, `python3 scripts/check_foundation.py`, `git diff --check`. Pour le test SMTP réel : `SH25_SMTP_TEST_HOST=localhost SH25_SMTP_TEST_HTTP=http://localhost:8025` avec Mailpit lancé.
