# SH-19 — Configuration versionnée du scoring

Le responsable recrutement peut nommer une configuration de poste, saisir ses quatre poids et valider une nouvelle version avec un motif obligatoire. Tous les membres du vivier peuvent consulter l’historique et choisir une version pour le prochain classement. La version 0 reste le défaut SH-18 ; enregistrer une configuration ne change pas implicitement les recherches des autres utilisateurs.

## Règles et gouvernance

- Capacité `CONFIGURE_SCORING` portée par le rôle `RECRUITMENT_LEAD` dans le vivier concerné. ADMIN seul ne donne aucun accès. La révocation et la validation partagent le verrou du compte.
- Quatre poids entiers entre 0 et 10 000 : obligatoires, souhaitées, exposition et récence. Somme strictement positive ; fractions, champs absents et valeurs négatives refusés côté serveur.
- Les groupes non demandés sont retirés puis les poids actifs sont normalisés. Une requête sans aucun poids actif positif est refusée (422), même sans résultat. Les composantes à poids nul sont retirées avant répartition des arrondis ; les obligations restent vérifiées.
- Version immuable avec poids avant/après, parts normalisées globales, auteur de validation, date et motif. Historique paginé par 25. `If-Match` obligatoire : une écriture concurrente périmée reçoit 412 et ne remplace aucune révision.
- La sélection explicite `configurationVersion` est figée avec les poids dans le snapshot. Une valeur absente ou nulle sélectionne 0. Les anciens snapshots SH-18 sans champ `policy` restent recalculables avec leurs poids initiaux et leur empreinte d’origine.
- Q reste un indicateur séparé du classement ; aucune qualité ni similarité ne multiplie le score. La demi-vie reste 36 mois. Responsabilité, certifications et secteur restent hors des dimensions structurées disponibles.

## Données et API

V16 ajoute `scoring_configuration`, clé `(pool_id, version)`, avec la révision sérialisée ; suppression en cascade avec le vivier. Aucun endpoint de modification ou suppression des versions. Aucun CV dans cet historique ; le nom et le motif doivent décrire le poste, sans données candidat.

Sous `/api/v1/pools/{poolId}/scoring-configurations` : GET état courant et droit de configuration, POST validation avec CSRF et If-Match, GET `/history` paginé et GET `/{version}`. Les snapshots privés conservent les règles de rétention, révocation et effacement SH-18.

## Vérifications

- `ScoringConfigurationTest` : permissions et accès croisés, révocation, CSRF, validation HTTP des entiers, poids invalides, historique et avant/après, conflit concurrent.
- `HumanReviewTest` : changement numérique indépendant (70 → 25 → 100), poids nuls, refus sans groupe actif, rejeu inchangé d’un snapshot personnalisé et d’un snapshot historique SH-18.
- Suite Java locale : 142 tests, 141 réussis et 1 test corpus ignoré faute de fixture PostgreSQL dédiée ; aucun échec. Build React/TypeScript et contrôle OpenAPI validés.
- Parcours Playwright ajouté à 1280 et 320 px, avec texte 200 % : habilitation responsable, création des poids, nouveau score, historique et rejeu du classement antérieur. La CI exécute ce parcours sur Compose/OIDC et les tests API sur PostgreSQL ; son résultat doit être vérifié sur la PR.
